## A8 相机被占用

| 项 | 内容 |
|---|---|
| 操作 | 先用系统相机占用相机 → 打开本应用相机页 |
| 判据 | 给出**可读提示**，不崩溃，相机可重试 |
| 已做的尝试（2026-09-11，全部失败于「造不出占用」而非「应用不行」） | ① 让系统相机（`com.huawei.hmos.camera`）在前台预览/录像，再切到本应用相机页 → 本应用**正常打开**（`准备就绪 · JPEG 4160x3120`）。hilog 给出原因：**系统相机被切到后台时会主动释放摄像头**（`com.huawei.hmos.camera/SessionWrap: session stop error: {"code":7400201,"message":"Camera service fatal error."}`），所以「切后台」这条路由根本造不出占用。<br>② 试图用 `aa start -W --wl/--wt/--ww/--wh` 把系统相机放进**浮动窗**（两个应用同时可见才能真占用）→ 实测无效：权限弹窗外的窗口参数 `-s <window-mode>` 标注为 **only for FA mode**，Stage 模型下仍是全屏。<br>③ 分屏（智慧多窗）只能靠手势/拖拽构造，`uitest` 无稳定路径。 |
| 用户侧补充实测（2026-09-11，用微信相机） | 「先开一个相机 → 再开另一个」的结果：**第二个能开，第一个不报错但画面静止**，按快门才抛 `拍摄失败：7400201 Camera service fatal error`。⇒ 鸿蒙的相机争用**不一定在 open 时报错**，可能表现为「静默失效 + 拍摄时才失败」。这条观察直接决定了我们的加固方向。 |
| 由上述观察做的加固（2026-09-11） | `CameraController` 在 `previewOutput` / `photoOutput` / `session` 上注册 `on('error')`，把异步错误立刻翻成 `相机连接中断（可能被其它应用占用）：<code> <message>`（不必等按快门）；`takePicture` 的 catch 保持返回 `拍摄失败：<code> <message>`；`open()` 改为先 `close()` 再开 + 页面双重幂等判据，避免两个 session 抢同一个 surface（这是「分屏时预览又扭曲」的最可能原因）。见 `ARCHITECTURE.md` §4.0 |
| 现有等效证据 | A8 依赖的失败分支与 A9 是**同一条代码路径**：`CameraController.open()` 的 `catch` → 返回可读串 → `CameraPage` 显示「相机启动失败：<code> <message>」，并保留可重试状态。A9 已实测该路径「可读文案 + 进程存活 + 其余功能可用」。**但「相机被占用」这个具体错误码从未在真机上观察到**，因此本项仍算未实测。 |
| 用户复现结果（2026-09-11） | 两个方向都试了：**先开微信 → 再切本应用：本应用相机完全正常，反而是微信出问题**；只有**先开本应用 → 再切微信**时，微信画面静止、按快门报 `7400201`。 |
| 结论（实测，2026-09-11） | **A8 的场景在本设备上不可构造**：鸿蒙把摄像头判给**前台**应用，被切到后台的持有者反而会释放/失效。也就是说「别的应用占着相机 → 本应用打不开」这种情况**不会发生**在本应用上（本应用永远是争用的赢家）。因此判据「被占用时给出可读提示」**不适用**；该条状态记为 **N/A（平台行为决定，非未测）**。 |
| 我们仍保留的防御（若将来真发生） | `CameraController` 已注册 `previewOutput`/`photoOutput`/`session` 的 `on('error')` → 立刻回显 `相机连接中断（可能被其它应用占用）：<code> <message>`；`takePicture` 失败回显 `拍摄失败：<code> <message>`（7400201 即此路径）；两条路径都由 A9 的同源分支证明过「可读文案 + 不崩溃」。 |
| 状态 | ➖ **N/A（不可构造）**：不是没测，而是平台把相机判给前台应用，争用中本应用总是赢。若要真构造，需要一个持有后台相机权限的应用（本机没有） |

## 结论

- **A1/A2/A3/A4/A6/A9 已在真机通过**（2026-09-11，全部由 `uitest` 自动驱动）；
  **A5 的缺陷已定位并修复，修复后真机通过**（A/B 对照量出根因是 `@State` 数组直传 native RDB）。
- **A4 有两条路径**，本轮都验了：无选中 → 删全部；有选中 → 只删选中（后者此前与 A5 同源损坏）。
- **A7（时钟回拨）/ A10（存储写满）**：CLI 无法构造（改系统时间、写满存储均不可自动化），
  以 L1 等价用例覆盖（A7 ↔ L1 用例 8；A10 ↔ 孤儿清理 8 条用例），**不谎报为真机通过**。
- **环境风险（非应用缺陷）**：本机 **纯净模式由系统强制开启且无法关闭**（系统帮助页原文，见 `docs/ENVIRONMENT.md` §8），
  本应用 `installSource=unknown`，会被系统**静默卸载**（实测 5 次）。当前用 `scripts/watch-app.sh` 兜住；
  根治需把应用发布到应用市场（T08 候选）。
- **A8（相机被占用）**：需要两个应用**同时可见**（后台的系统相机会释放摄像头，已实测 7400201），
  而 Stage 模型下 `aa start` 无法把应用放进浮动窗（窗口参数仅 FA 模式有效）。因此只能人工在**分屏**下验，
  步骤见 `tasks/T06-e2e-acceptance.md`；未实测，**不算通过**。
- **A9（拒绝相机权限）**：本轮才真正验完（干净重装 → 点「不允许」→ 复查 `bm dump` 为 `-1` →
  页面给出可读引导、进程存活、待删除页仍可用）。此前结论段写过「A9 通过」但条目里是「未执行」，
  属**前后不一致**，已按实测证据统一为通过。
- 替代证据：L1 **56** 条用例（状态机、到期边界、幂等、时钟回拨、删除语义、孤儿清理、统计、
  **napi 边界回归 6 条**）+ 真机自检 `domainSmoke=PASS` / `storageSmoke=PASS`
  （走生产代码路径的 RDB/沙箱/preferences；本轮新增 `keep` 契约用例与 `proxyProbe` 对照实验）。
